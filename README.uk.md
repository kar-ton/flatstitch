# flatstitch

*[Read this in English](README.md)*

Інструмент для Linux (консоль + графічний інтерфейс), який зшиває
скановані зображення в одне безшовне TIFF-зображення. За призначенням —
аналог Microsoft ICE (Image Composite Editor), але свідомо звужений під
конкретну задачу: **склеювання плоских сканів**, а не фотопанорам.

Є два способи запуску, обидва використовують те саме ядро (пакет
`flatstitch/`):
- **`flatstitch-gui.sh`** — повноцінний графічний інтерфейс: додайте
  скани (кнопкою або перетягуванням), налаштуйте параметри, натисніть
  «Зшити» і побачите живий журнал прогресу та результат прямо у вікні.
- **`flatstitch.sh`** — консольний варіант, зручний для скриптів і
  пакетної обробки.

Доступний 10 мовами (визначається автоматично з мови системи, або
оберіть явно): українська, англійська, іспанська, французька, німецька,
португальська (Бразилія), італійська, польська, спрощена китайська та
японська.

## Чому не просто "клон ICE"

ICE та більшість панорамного ПЗ (Hugin, PTGui тощо) розраховані на фото,
зняті на камеру: там є перспектива, дисторсія об'єктива, паралакс — тому
такі програми підганяють між кадрами повну гомографію (проєктивне
перетворення "у 8 ступенів свободи"), яка вміє "нахиляти" зображення як
трапецію.

Скан з планшетного сканера — це фізично інша ситуація: аркуш лежить на
склі рівно, тому між двома сусідніми сканами немає ні перспективи, ні
зміни масштабу — є лише невеликий поворот (якщо аркуш поклали не зовсім
рівно) і зсув. Тому flatstitch свідомо шукає **жорстке перетворення**
(поворот + зсув, масштаб завжди = 1), а не гомографію. Це не спрощення
заради спрощення: та сама кількість зіставлених точок ознак дає
набагато стійкішу оцінку, коли модель має менше степенів свободи, а
результат геометрично не може "перекосити" прямі лінії й текст — саме
це найчастіше псує спроби зшити скани загальним панорамним ПЗ.

## Встановлення через .deb пакет (рекомендовано)

Найпростіший спосіб на Linux Mint / Ubuntu - встановити готовий пакет
`flatstitch_1.0.1-1_all.deb`:

```bash
sudo apt install ./flatstitch_1.0.1-1_all.deb
```

Це встановить `flatstitch` (CLI) і `flatstitch-gui` (GUI) у PATH, додасть
застосунок у меню програм (з іконкою) і **автоматично** створить
окреме, ізольоване середовище Python у `/opt/flatstitch/venv` та
встановить туди всі потрібні бібліотеки (OpenCV, NumPy, SciPy тощо) -
системний Python при цьому не зачіпається. Для цього кроку потрібне
інтернет-з'єднання і може знадобитися кілька хвилин.

**Якщо `apt install ./файл.deb` пише, що не може прочитати файл**
(щось на кшталт «недоступний для користувача `_apt`») - це трапляється
тому, що домашні теки зазвичай непридатні для читання непривілейованим
користувачем, від імені якого apt завантажує файли. Зазвичай це
нешкідливо (apt просто читає файл від імені root замість цього), але
якщо встановлення дійсно не вдається, найнадійніше — встановити напряму
через dpkg:

```bash
sudo dpkg -i ./flatstitch_1.0.1-1_all.deb
sudo apt-get install -f -y   # довстановить відсутні залежності
```

**Якщо у вас проксі** і встановлення залежностей не вдалося (про це
буде явне повідомлення після встановлення пакета - сам пакет при цьому
все одно встановиться успішно, просто без робочих залежностей) -
`postinst` спершу сам пробує підхопити проксі з налаштувань apt
(`Acquire::http::Proxy`), а якщо там нічого немає - виведе готову
команду для ручного встановлення. В обох випадках проксі з вашого
звичайного `~/.bashrc`/оточення тут не побачити: `sudo`/`apt`
запускають postinst-скрипти в мінімальному, ізольованому оточенні, і
навіть `sudo -E` цього не змінює. Команда для ручного встановлення:

```bash
sudo http_proxy=http://ХОСТ:ПОРТ https_proxy=http://ХОСТ:ПОРТ \
    /opt/flatstitch/venv/bin/pip install -r /opt/flatstitch/requirements.txt
```

Видалення (акуратно прибирає і venv, і сам пакет):

```bash
sudo apt remove flatstitch
```

**Про значок у меню**: одразу після встановлення деякі стільниці
(включно з Cinnamon) підхоплюють щойно доданий пункт меню — разом зі
значком — лише після наступного перезапуску чи входу в систему; це
звичайна поведінка стільничного середовища, а не ознака помилки. Якщо
значок все ще типовий після повторного входу, виконайте `sudo
update-icon-caches /usr/share/icons/hicolor` (або ще раз вийдіть/зайдіть
в систему).

### Збірка .deb з вихідного коду

Якщо ви зміните код і захочете перезібрати пакет - структура для
`dpkg-deb` лежить у теці `deb/flatstitch_1.0.1-1_all/`. Після правок:

```bash
sudo apt install fakeroot        # одноразово, якщо його немає
cd deb
fakeroot dpkg-deb --build --root-owner-group flatstitch_1.0.1-1_all
```

## Встановлення з вихідного коду (без .deb)

Якщо не хочете встановлювати системно - розпакований `flatstitch/` із
цього архіву працює повністю самостійно через wrapper-скрипти нижче,
без dpkg/root-прав.

Потрібен Python 3.9+.

```bash
cd flatstitch
pip install -r requirements.txt
# або, якщо система блокує системний pip:
pip install --break-system-packages -r requirements.txt
```

Для GUI додатково потрібен системний пакет Tk (не встановлюється через
pip):

```bash
sudo apt install python3-tk
```

Перетягування файлів у вікно GUI - опціональна можливість (пакет
`tkinterdnd2` з requirements.txt). Без нього GUI працює повністю, просто
без drag-and-drop - додавайте файли кнопкою «Додати файли...».

Якщо інтернет у вас іде через проксі і pip його сам не підхоплює,
вкажіть проксі явно:

```bash
pip install --proxy http://ХОСТ:ПОРТ -r requirements.txt
```

## Швидкий старт

Скрипт `flatstitch.sh` можна викликати з будь-якої директорії — вхідні
й вихідні шляхи розуміються відносно того місця, де ви зараз, а не
теки самого інструменту:

```bash
/шлях/до/flatstitch/flatstitch.sh скан1.png скан2.png скан3.png

# або передати всю теку зі сканами:
/шлях/до/flatstitch/flatstitch.sh ./скани/
```

**Куди зберігається результат:** якщо `-o` не вказано, файл автоматично
зберігається як `stitched.tiff` у тій самій теці, де лежить перший
вхідний скан (якщо така назва вже зайнята - `stitched_2.tiff`,
`stitched_3.tiff`, ... - наявні файли ніколи не перезаписуються мовчки).
Щоб задати шлях самостійно:

```bash
/шлях/до/flatstitch/flatstitch.sh ./скани/ -o /інший/шлях/результат.tiff
```

У GUI те саме поле «Зберегти як» заповнюється автоматично тим самим
шляхом одразу після додавання перших сканів, і його можна вільно
відредагувати або обрати інший через «Огляд...».

Якщо запускаєте без wrapper-скрипта через `python3 -m`, потрібно
перебувати саме в теці `flatstitch` (тій, де лежить `requirements.txt`):

```bash
cd flatstitch
python3 -m flatstitch.cli ./скани/
```

Порядок файлів у команді **не має значення** — інструмент сам знаходить,
які скани з якими межують, за спільними ознаками (лініями, текстом,
деталями зображення), так само як це робить ICE. Це працює як для
одного рядка сканів, так і для сітки (рядки×стовпці), і навіть для
довільного, наперед невідомого розташування.

## Як це працює (коротко)

1. **Пошук ознак** — SIFT (за замовч.) або ORB на кожному скані.
2. **Зіставлення всіх пар сканів** — для кожної пари шукаються спільні
   точки, і жорстке перетворення (поворот+зсув) оцінюється через RANSAC
   з адаптивною зупинкою (менше ітерацій, коли модель вже впевнено
   хороша), щоб відкинути помилкові збіги. При кількох ядрах процесора
   пари обробляються паралельно (`--jobs`) - саме ця частина росте
   як n², тож паралелізм тут дає найбільший ефект при більшій кількості
   сканів.
3. **Побудова спільного розташування** — з надійних пар будується
   "дерево" початкового розташування всіх сканів у спільних координатах,
   а тоді (за наявності 3+ пов'язаних сканів) виконується глобальне
   уточнення (bundle adjustment): усі скани одночасно трохи
   підлаштовуються так, щоб сумарна похибка на *всіх* знайдених парах
   (не лише на "дереві") була мінімальною. Це прибирає накопичення
   похибки, яке інакше наростає, якщо сканів багато і вони йдуть
   ланцюжком.
4. **Потокова проєкція на полотно й змішування** — кожен скан по черзі
   зчитується з диска, переноситься на *свою власну* ділянку спільного
   полотна (`warpAffine` з кубічною інтерполяцією, без жодної
   проєктивної деформації) і одразу додається у два наскрізні
   накопичувачі, після чого вивантажується з пам'яті - на екрані одразу
   тримається не більше одного скану плюс саме полотно, а не по копії
   полотна на кожен скан (детальніше - розділ "Продуктивність" нижче).
   У зонах перекриття пікселі змішуються з вагою за відстанню до краю
   скану, підсиленою до майже "чіткого" шва — це зберігає різкість ліній
   і тексту (на відміну від широкого фезерингу чи multi-band blending,
   які тонкі лінії/текст помітно розмивають).
5. **Обрізка й збереження** — полотно обрізається до фактично заповненої
   області (порожні поля через невеликий поворот прибираються), і
   результат зберігається як TIFF (LZW за замовч., без втрат; великі
   результати автоматично зберігаються як BigTIFF).

## Фон і орієнтація результату

**Фон за замовчуванням прозорий.** Ділянки полотна, які не покриває
жоден скан — зазвичай лише тонкі клинці по краях, де аркуш лежав на склі
трохи криво — записуються як альфа-канал, а не замальовуються. Кольоровий
результат стає RGBA, відтінки сірого — сірий+альфа, і у 8-, і у 16-бітному
варіанті. Альфа позначається як неасоційована (straight, не
premultiplied), а RGB під прозорими пікселями все одно заповнюється
білим — тож програма чи інструмент, який альфа-канал ігнорує, покаже
рівно те саме, що давала версія 1.0.0, а не чорну рамку.
`--background white` або `--background black` замальовують ці ділянки й
не пишуть альфу взагалі.

Ціна — заміряна, а не припущена (16 сканів, полотно ~5400x4000):

| | непрозорий | прозорий |
|---|---|---|
| пікова RAM | 1188304 КБ | 1188376 КБ (+0,006%) |
| час | 78,6 с | 79,6 с |
| розмір файлу | 6,96 МБ | 8,97 МБ (+29%) |

Пікова пам'ять майже не змінюється, бо альфа-канал додається *після*
того, як float32-накопичувачі вже звільнено, тож він ніколи не існує
одночасно зі справжнім максимумом споживання. На меншому наборі з
повторними прогонами (5 запусків, за найкращим) прозорість коштувала
близько 3% часу. Справжня ціна — **розмір файлу**: четвертий канал, який
LZW стискає добре, але не до нуля. Якщо розмір важливіший за прозорість,
використовуйте `--background white`.

**Повернуті скани (90/180/270) і автоповорот.** Аркуші, покладені на скло
боком або догори дриґом, обробляються, і це не коштує практично нічого —
що варто пояснити, бо це властивість самої архітектури, а не функція, яку
довелося доробляти:

- дескриптори SIFT і ORB *інваріантні до повороту* за побудовою, тож
  ознаки скану, що лежить боком, безпосередньо зіставляються з ознаками
  сусіднього рівного скану;
- геометрична модель — жорстке перетворення з повною матрицею повороту
  2x2, тож 90 градусів виразити не важче, ніж 0,5 градуса.

Заміряно на однакових фрагментах: один набір рівний, другий повернутий на
90/180/270 (одне ядро, 5 повторів, за найкращим):

| | рівні | повернуті 90/180/270 |
|---|---|---|
| SIFT | 6,92 с, зіставлено 6/6 пар | 7,07 с, зіставлено 6/6 пар |
| ORB | 3,58 с, зіставлено 6/6 пар | 3,53 с, зіставлено 6/6 пар |
| пікова RAM | 421716 КБ | 421780 КБ |

Кількість інлаєрів відрізнялася на кілька відсотків в обидва боки (SIFT:
797/776/688... для рівних проти 806/804/668... для повернутих), тож якість
зіставлення не деградує.

А от що справді потребувало виправлення — річ тонша, і її виявило
тестування, а не міркування: розташування будується відносно одного
опорного скану, тому полотно успадковує орієнтацію **саме його**.
Зшивання завжди було правильним, але якщо опорним виявлявся той, що лежав
боком, усі інші фрагменти доверталися під нього — і готовий аркуш виходив
боком, із текстом на боці.

Тому тепер полотно повертається на кратне 90 градусів так, щоб більшість
фрагментів вийшла в тій орієнтації, в якій їх сканували. Оскільки
застосовуються лише точні чверті обороту, додаткової ресемплінг-похибки
не виникає — кожен фрагмент однаково warp-иться рівно один раз — а сам
крок займає близько **136 мікросекунд на 64 фрагменти**. Коли всі скани
вже узгоджені (звичайний випадок), обраний кут дорівнює 0 і не змінюється
абсолютно нічого, тож попередня поведінка не зачіпається.

Це евристика, а не магія: вона припускає, що більшість аркушів покладено
рівно, бо сама лише геометрія не може знати, як документ «має» бути
орієнтований. Якщо більшості немає — скажімо, чотири фрагменти в чотирьох
різних поворотах — вона відмовляється вгадувати й лишає орієнтацію без
змін. Нічия теж вирішується на користь «не змінювати».
`--no-auto-orient` вимикає це повністю.

## Продуктивність і пам'ять

Це не перше формулювання цього розділу - нижче зафіксовано, що саме
змінилося після зовнішнього рев'ю коду першої версії, і чому.

- **Пам'ять більше не росте з кількістю сканів.** Перша версія
  переносила КОЖЕН скан на полотно ПОВНОГО розміру перед змішуванням -
  для полотна 15000×15000 це ~645МБ на скан, і для 50 сканів це вже
  30+ ГБ лише на проміжні копії. Тепер кожен скан переноситься лише у
  свою власну (набагато меншу) ділянку і одразу додається у спільний
  накопичувач - пам'ять залежить від розміру полотна плюс розмір ОДНОГО
  скану, а не від їх кількості. На тесті 16 сканів/полотно ~5400×4000
  пікове споживання - **~1.2 ГБ** (виміряно `/usr/bin/time -v`).
  Накопичувачі також переведено з float64 на float32 - вдвічі менше
  пам'яті, точності більш ніж достатньо для 8/16-бітних сканів.
- **Оригінали не тримаються в пам'яті всі одразу.** Кожен скан
  завантажується з диска для пошуку ознак, після чого вивантажується;
  для самого зшивання він завантажується повторно, по одному. Це
  означає одне зайве читання з диска на скан, що для звичайних файлів
  сканів - мілісекунди, і незрівнянно дешевше за ризик вичерпання
  оперативної пам'яті.
- **Зіставлення пар сканів можна розпаралелити** (`--jobs N`, GUI:
  «Паралельні процеси»). За замовчуванням використовує всі ядра
  процесора. Це саме той етап, що росте як n² з кількістю сканів, тож
  ефект помітніший при більших наборах; для 2-3 сканів (1-3 пари)
  інструмент просто виконує їх послідовно в тому ж процесі, без
  накладних витрат на запуск окремих процесів.
- **RANSAC зупиняється раніше, коли це безпечно** (стандартна
  адаптивна формула на основі поточної частки інлаєрів), замість
  завжди виконувати фіксовані 3000 ітерацій. Разом зі зміною
  інтерполяції (нижче) це дало ~20% пришвидшення в тестах навіть без
  жодного паралелізму.
- **Інтерполяція за замовчуванням - `cubic`, а не `lanczos4`.**
  Lanczos різкіший на фотографіях, але його широке ядро дає помітний
  ефект "дзвону" (ringing) - мікроореоли навколо різких країв, що на
  сканах тексту й креслень виглядає як слабкі тіні навколо букв і
  ліній. Cubic зберігає майже ту саму різкість з набагато меншим
  ringing. `--interpolation lanczos4/linear/nearest` - якщо потрібен
  інший компроміс.

**Свідомо не зроблено (поки що):**
- *Компіляція RANSAC через numba (`@njit`)* - дала б додаткове
  пришвидшення однієї пари, але numba - важка, примхлива у встановленні
  залежність (конкретні версії llvmlite, повільна перша компіляція) для
  інструменту, який мав лишатися простим `pip install`. Паралелізм між
  парами (вище) дає приріст того ж порядку без цієї ціни.
- *Розріджений Якобіан (`jac_sparsity`) для bundle adjustment на
  сотнях сканів.* Тут варто уточнити: у пропозиції, з якої походить ця
  ідея, був вказаний неіснуючий параметр `sparse_jacobian=True` -
  реальний параметр `scipy.optimize.least_squares` називається
  `jac_sparsity` і очікує саму матрицю/патерн розрідженості, яку
  потрібно коректно побудувати (яка ваша помилка впливає на які
  параметри). Помилка в такому патерні - це вже не питання швидкості, а
  ризик тихо неправильного результату, тож без ретельної перевірки на
  великих наборах я свідомо не став це вносити зараз. Для реалістичної
  кількості сканів (одиниці-десятки) щільний Якобіан і так достатньо
  швидкий.

## Поради для якісного результату

- **Перекриття 15-30%** між сусідніми сканами — як і в ICE/панорамній
  фотографії. Менше — може не вистачити спільних ознак.
- **У зоні перекриття мають бути деталі** (лінії, текст, дрібні
  об'єкти). Суцільне чисте поле без жодних деталей зіставити неможливо
  в принципі (це стосується будь-якого інструменту на основі ознак, не
  лише цього).
- Великий випадковий поворот аркуша на склі (у тестах — вже за ±2°)
  залишає помітні білі "клинці" по краях зшитого результату (інструмент
  сам про це попередить у виводі). За акуратного сканування (поворот
  до ~1°) це непомітно.

## Основні опції

| Опція | Призначення |
|---|---|
| `-o, --output` | шлях до вихідного TIFF. Необов'язково - за замовч. `stitched.tiff` у теці першого вхідного файлу |
| `--detector sift\|orb` | детектор ознак; sift точніший, orb швидший |
| `--jobs N` | кількість процесів для паралельного зіставлення пар сканів. За замовч. - всі ядра процесора |
| `--interpolation cubic\|linear\|lanczos4\|nearest` | метод інтерполяції при повороті сканів (див. розділ "Продуктивність"); за замовч. `cubic` |
| `--downscale N` | зменшити зображення в N разів лише для пошуку ознак (пришвидшує обробку дуже великих сканів, на якість фінального зшивання майже не впливає, бо саме зшивання все одно відбувається у повній роздільній здатності) |
| `--min-inliers N` | скільки узгоджених точок потрібно, щоб вважати два скани пов'язаними (за замовч. 12; зменшіть, якщо в зоні перекриття мало деталей) |
| `--no-bundle-adjust` | вимкнути глобальне уточнення (лише для дуже великих наборів, якщо важлива швидкість) |
| `--background transparent\|white\|black` | що робити з непокритими ділянками; `transparent` (замовч.) пише альфа-канал, інші — замальовують |
| `--no-auto-orient` | не повертати готовий аркуш до орієнтації більшості |
| `--compression lzw\|zlib\|none` | стиснення TIFF |
| `--lang` | мова інтерфейсу; за замовч. визначається з мови системи |
| `-v` | докладний вивід (що з чим зіставилось, скільки інлаєрів) |

Повний список: `./flatstitch.sh --help`

## Якщо щось пішло не так

- **"Жодної пари зображень не вдалося зіставити"** — перевірте, що
  сусідні скани справді перекриваються і в зоні перекриття є деталі;
  спробуйте зменшити `--min-inliers`.
- **"Зображення утворюють N незв'язані групи"** — частина сканів не
  знайшла спільних ознак з рештою (недостатнє перекриття або немає
  спільних деталей); кожна група зберігається окремим файлом
  (`_part1.tiff`, `_part2.tiff`, ...), щоб ви не втратили вже
  оброблені дані.
- **Помітні білі клинці по краях** — збільшіть перекриття або
  акуратніше кладіть аркуш на скло.

## Додавання мови

Переклади лежать у `flatstitch/locales/<код>.json` — звичайний JSON, по
одному короткому ключу на рядок інтерфейсу. Щоб додати нову мову:

1. Скопіюйте `flatstitch/locales/en.json` у `<код>.json` (базовий код
   мови, напр. `nl` для нідерландської, або `pt_BR`-подібний формат для
   регіонального варіанту).
2. Перекладіть кожне значення; імена `{плейсхолдерів}` усередині рядків
   не чіпайте (їх підставляють числа/шляхи тощо під час роботи).
3. Зареєструйте мову в `SUPPORTED_LANGUAGES` у `flatstitch/i18n.py`
   (назва англійською і рідною), і, якщо оновлюєте також пакунок,
   додайте рядки `Name[<код>]=`/`Comment[<код>]=` у `.desktop`-файл.
4. Перевірте: `python3 -c "from flatstitch import i18n; import json;
   en=json.load(open('flatstitch/locales/en.json'));
   x=json.load(open('flatstitch/locales/<код>.json'));
   print(set(en)-set(x), set(x)-set(en))"` має вивести дві порожні множини.

Мови з написанням справа наліво (арабська, іврит тощо) поки не додані —
у Tkinter немає вбудованого дзеркального RTL-макета, тож для повноцінної
підтримки знадобиться додаткова робота над інтерфейсом, а не лише
переклад рядків. Допомога вітається.

## Обмеження / що можна додати в майбутньому

- Розраховано на малі повороти (акуратне сканування). Аркуші,
  повернуті на 90°/180°, потрібно попередньо зорієнтувати самостійно.
- Усі пари зображень порівнюються між собою (O(n²)) - з `--jobs` це
  добре масштабується на десятки сканів; для сотень варто буде додати
  попередній відбір кандидатів (щоб не перевіряти взагалі всі пари).
- Шов будується через "загострений" фезеринг за відстанню, а не через
  повноцінний пошук оптимального шва (graph cut) — для сканів
  документів цього зазвичай достатньо, але для складних випадків
  (дрібний текст точно на межі перекриття) точний seam-carving дав би
  ще кращий результат.
- Розріджений Якобіан для bundle adjustment на дуже великих наборах
  (сотні сканів) - див. пояснення в розділі "Продуктивність" вище.
